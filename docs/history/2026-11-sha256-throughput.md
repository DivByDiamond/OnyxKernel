# SHA-256: пропускная способность и время логина (2026-11)

Оптимизация `onyx_core::crypto::sha256` — единственного по-настоящему
CPU-bound пути в userspace: `kdf::hash_password` (10 000 раундов) и
`sha256crypt::digest` (`$5$`, 5000 раундов по умолчанию) выполняются при
каждом логине (`onyx-login`, `passwd`, `su`, `useradd`, `userdel`).
В ядро `sha256` не попадает, поэтому образ ядра не меняется
(`.text` = 223 814 B до и после).

## Диагноз (до изменений)

Стенд: Intel Xeon E5-2680 v3 (24 потока), Linux 7.2.14, rustc 1.99.1,
профиль = kernel release (`opt-level = "z"`, `overflow-checks`, `lto = false`,
`codegen-units = 1`). Замер — отдельный host-крейт в `/home/loki/onyx-bench-work`,
линкующий `onyx_core` по пути (репозиторий и его `Cargo.toml` не менялись).

`perf stat -r 3 -e cycles,instructions,... ./onyx-bench once 1048576 8`:

| метрика | значение |
|---|---|
| инструкций на байт | 74.7 |
| циклов на байт | 24.1 |
| IPC | 3.1 |
| cache-misses | ~0.06 на 1 KiB |

Классификация: **CPU-bound по числу инструкций** (высокий IPC, кэш не при чём).
Два источника:

1. `sha256_update` складывал данные в буфер **побайтово**:
   `cmp $0x40 / jae panic`, запись в `[r15+rdi]`, `inc`, `incq`, `cmp $0x40,
   jne` — ~13 инструкций и 3 ветвления на каждый байт, плюс проверка
   переполнения `total_len`.
2. `sha256_compress` держал `w: [u32; 64]` (256 B, с `memset` на каждый блок),
   оба цикла — с динамическими индексами, а в RISC-V кодогенерации каждый
   раунд заканчивался 8 `mv` для поворота `a..h` (52 инструкции на раунд).

Динамическая стоимость на блок (RISC-V, статический подсчёт тел циклов):
16 загрузок × 22 + расписание 48 × 29 + раунды 64 × 52 ≈ **5282** инструкции.

## Контракт (что обязано было остаться идентичным)

- digest побайтово совпадает для любого входа; публичный API
  (`sha256_init/update/final/sha256`, `Sha256State` с приватными полями) не менялся;
- `no_std`, без аллокаций, без `unsafe`, без `unwrap`/`panic`-путей на входе;
- поведение при пустых чанках, чанках через границу 64 B и на точных кратных
  64 B — то же, что у one-shot.

Проверка: KAT (RFC 6234 + границы 55/56/57/63/64) + дифференциальный тест
против замороженной копии старого `sha256.rs` (603 случая: длины 0…600,
чанки 1/3/17/31/63/64/65/127, пустой `update`, 4 KiB/64 KiB+1/1 MiB).

## Изменения

1. `sha256_update`: побайтовый цикл заменён на дозаполнение буфера одним
   `copy_from_slice`, затем `data.as_chunks::<64>()` — полные блоки
   сжимаются прямо из слайса вызывающего, хвост копируется в буфер.
2. `sha256_compress` вынесен в `core/src/crypto/sha256/compress.rs`:
   - расписание — 16 слов с накоплением (`w[t & 15]`), без `memset` и без
     256-байтного массива (кадр стека 368 → 320 B на RISC-V);
   - 64 раунда развёрнуты макросом `round!`, переменные передаются в
     повёрнутом порядке — без `mv`-каскада;
   - `rotr(x, n)` → `u32::rotate_right(n)`, `ch`/`maj` — в формах
     `z ^ (x & (y ^ z))` и `(x & y) | (z & (x | y))`;
   - `w[0..16]` инициализируется литералом с константными индексами
     (убирает `memset` и цикл загрузки).
3. Тест `chunked_update_all_chunk_sizes_match_one_shot` в
   `core/src/crypto/tests/sha256.rs` (каждая ветка `update`).

## RISC-V: инструкции и размер

Статический подсчёт по `objdump` собранного `onyx-login`:

| | до | после |
|---|---|---|
| инструкций на 64-байтный блок | 5282 | 3876 (**−26.6 %**) |
| `.text` `onyx-login` | 21 964 B | 33 686 B (**+11.7 KB**) |

Цена — развёрнутый код. Компактный вариант (разворот на 8 раундов,
`compress-8.rs`) даёт `.text` 26 924 B (+5 KB), но на 12…21 % медленнее
полного разворота, поэтому не выбран.

## Отвергнутые / неизмеренные варианты

- **8-раундовый разворот** — измерен: +12…21 % времени против полного
  разворота; выигрыш только в размере. Оставлен как компромисс на случай
  дефицита flash.
- **Специализация KDF под один блок** (готовый блок `h || salt || padding`):
  по замеру накладные расходы `update+final` — ~14 ns из 405 ns на раунд
  (~3.5 %), не окупает API-усложнение. Не реализовано.
- **Сборка сообщения `sha256crypt` в один буфер** (вместо 5 вызовов `update`
  на раунд): до `-O3` остаток был ~47 ns/раунд (~11 %), после override
  накладные расходы исчезли — 308 ns/раунд против 322 ns на одиночный
  55-байтный блок. Не реализовано: измерять больше нечего.
- **`unsafe`/SIMD** не использовались: на RISC-V нет аппаратного SHA и
  rotate-инструкций (`rv64gc` без Zbb), выигрыш не доказан.

## Профиль: `onyx_core` отдельно на `-O3` (применено)

`[profile.release] opt-level = "z"` общий для workspace, но точечный
override разрешён Cargo: `[profile.release.package.onyx_core] opt-level = 3`.
Замер (тот же стенд, `bin-final2` = всё на `-Oz` против `bin-pkg-o3`):

| случай | `-Oz` | `onyx_core` `-O3` | Δ |
|---|---|---|---|
| `hash_password` 10k | 3.67 ms | 2.97 ms | −19.0 % |
| `$5$` `digest` 5000 | 1.98 ms | 1.54 ms | −22.3 % |
| sha256 0/1 B | 455/458 ns | 380/379 ns | −16.4 % |
| sha256 64 B | 711 ns | 636 ns | −10.6 % |
| sha256 1 MiB | 4.30 ms | 4.34 ms | +0.4 % (шум, 5 раундов: −0.3…+0.4 %) |

Итог относительно исходного HEAD: KDF **5.47 → 3.03 ms (−44.6 %)**,
`sha256crypt` **2.89 → 1.52 ms (−47.3 %)**, sha256 1 MiB **−48.6 %**,
64 KiB **−49.0 %**, 64 B **−39.0 %**, 0/1 B **−28 %**.

Цена по размеру (`.text`, RISC-V):

| бинарник | `-Oz` | +override | Δ |
|---|---|---|---|
| `onyx-login` | 33 686 | 38 226 | +4.5 KB |
| `onyx-passwd` | 30 261 | 34 845 | +4.6 KB |
| `onyx-su` | 25 561 | 29 515 | +4.0 KB |
| `onyx-useradd` | 28 928 | 32 272 | +3.3 KB |
| `onyx-userdel`/`onyx-init`/`onyx-groups` (без крипты) | — | — | 0 |
| ядро (text+rodata) | 287 570 | 285 539 | −2.0 KB |

Итого +16.4 KB на образ, ядро не растёт. Для путей, которые хешируют
большие буферы, `-O3` не даёт ничего (сейчас таких вызовов в системе нет —
`sha256` используется только в auth).
