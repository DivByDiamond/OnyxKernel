### 🔥 Найдено и починено при живом тесте ohttp в QEMU (2026-09-01)
Тестировал `OnyxApps/apps/ohttp` в QEMU (`-netdev user` + `guestfwd`); по ходу
нашлись и почищены два системных бага, плюс остался один открытый:

- [x] **Errno не транслировался в POSIX** — `core/src/errno.rs::Errno::as_i64()`
      отдавал «сырой» внутренний ordinal (`Ok=0, NoMem=-1, Inval=-2, NoEnt=-3,
      Io=-4, Perm=-5, ...`), и именно это число (после отрицания) попадало в
      userspace `errno`, хотя `libonyxc/include/io/errno.h` документирует и
      определяет POSIX/glibc-значения (`ENOENT=2, EIO=5, EACCES=13, ...`) и
      прямо утверждает, что трансляция уже происходит. Добавлены
      `Errno::to_posix()` / `Errno::from_i64()` / `Errno::translate_syscall_result()`
      (`core/src/errno.rs`, покрыты host-тестами) и единая точка перевода в
      `kernel/src/syscall/handler/dispatch.rs::handle()` (оборачивает и ACL-early-return,
      и результат матча по `nr`). Подтверждено живьём: `ohttp` до фикса получал
      `errno=4` (сырой `Io`), после фикса — `errno=5` (POSIX `EIO`).
- [x] **virtio-net не настраивал отдельную TX-очередь (queue 1)** —
      `send()` писал в те же кольца, что `setup_rx_queue` завела для очереди 0
      (RX), и уведомлял `R_QUEUE_NOTIFY` со значением `0` — то есть говорил
      устройству «в RX есть новые буферы» вместо «вот кадр на отправку», и
      затирал RX-дескрипторы 0/1. Заведена отдельная TX-очередь (`queue 1`,
      как у `virtio_console` — см. `kernel/src/drivers/virtio_console/mod.rs`
      для образца), `send()` теперь пишет в `G_NET.tx_*` и уведомляет
      `R_QUEUE_NOTIFY=1` (`kernel/src/drivers/virtio_net/mod.rs`,
      `kernel/src/drivers/virtio_net/xfer.rs`).
- [x] **virtio-mmio регистрировал очереди только по modern-протоколу (v2)** —
      реальный `qemu-system-riscv64 -device virtio-net-device` под `-M virt`
      по умолчанию отдаёт **legacy** транспорт (`R_VERSION=1`), у которого нет
      регистров `R_QUEUE_{DESC,AVAIL,USED}_*`/`R_QUEUE_READY` — вместо них
      нужен один `R_QUEUE_PFN` на физически смежный регион
      desc|avail|used, плюс `R_GUEST_PAGE_SIZE`/`R_QUEUE_ALIGN`. Драйвер писал
      только modern-регистры, так что на legacy-транспорте очередь физически
      никогда не «вооружалась» — отсюда 0 пакетов на pcap. Добавлен общий
      `setup_queue_rings(base, modern)` с legacy-веткой (по образцу
      `kernel/src/drivers/virtio/queue.rs::setup_queue`, который у virtio-blk
      уже делал это правильно). **Подтверждено pcap'ом**: до фикса — 0 пакетов
      за весь бут; после — полный DHCP DISCOVER/REPLY, ARP REQUEST/REPLY,
      TCP SYN → SYN-ACK от пира.
- [x] **DHCP OFFER доходил до RX-буфера корректно, но не засчитывался; TCP
      SYN-ACK матчился с той же ошибкой** — оба `handle_udp_inner`
      (`kernel/src/net/udp/rx.rs`) и `handle_tcp_inner`
      (`kernel/src/net/tcp/handle.rs`) читали src/dst port **в обратном
      порядке**: UDP/TCP-заголовок (RFC 768/793) кладёт source port в байты
      0-1, destination port — в байты 2-3, а оба обработчика были написаны
      наоборот. Для UDP это ломало `sock.local_port == dst_port` (сравнение
      шло с полем source вместо destination — наш сокет на 68 порту никогда
      не матчился с ответом сервера). Для TCP аналогично ломало 4-tuple
      матчинг `c.src_port != dport || c.dst_port != sport` — реальный
      SYN-ACK/ACK никогда не находил живое соединение. **Подтверждено живьём
      end-to-end**: до фикса — DHCP всегда фоллбэк на захардкоженный IP,
      `tcp_connect` — таймаут; после фикса — `[INF] net: DHCP lease
      acquired`, полный TCP handshake+data+FIN с реальным сервером через
      `ohttp` (см. `OnyxApps/todo.md`).
- [x] **`usleep()`/`nanosleep()` зависал навсегда** (2026-09-02, **фикс
      подтверждён живым QEMU-тестом**). Диагностика прошла через 3
      отвергнутых гипотезы (см. git-историю этой строки для деталей) до
      найденного через monitor `info registers` root cause: CLINT
      `mtimecmp` MMIO-компаратор взводит только `mip.MTIP` —
      M-mode-only прерывание, которое RISC-V `mideleg` в принципе не
      может делегировать в S-mode. Кастомный M→S переход ядра при
      загрузке (`arch/asm/boot.rs`) обнулял `mie` и один раз делал
      `mret`, никогда не возвращаясь в M-mode — MTIP→STIP форвардинг не
      происходил вообще, и любой `wfi` в S-mode, ждущий таймер (включая
      `idle.rs` на реально простаивающем харте), не мог проснуться.
      Пробовал современный обход через Sstc (`stimecmp`) — не сработал,
      эта сборка QEMU (`11.1.1`, `-M virt`) не даёт S-mode доступ к
      `stimecmp` даже с `-cpu max`; откачено.
      **Итоговый фикс**: минимальный M-mode trap-хендлер
      (`kernel/src/arch/asm/mtrap.rs`, `mtrap_entry`), реализующий
      классический legacy SBI v0.1 `SBI_SET_TIMER` (уже был частично
      готов — `arch::sbi::set_timer()` раньше использовался только
      `smode`/OC2R-сборкой против настоящего OpenSBI). Обработчик ловит
      два случая: (1) `ecall` из S-mode (бит 9 medeleg намеренно НЕ
      делегирован — раньше был, теперь ловится в M-mode) — пишет CLINT
      `mtimecmp` текущего харта, чистит `mip.STIP`, включает `mie.MTIE`;
      (2) machine timer interrupt (cause 7, не делегируем в принципе) —
      выставляет `mip.STIP` (проброс в S-mode, где `mideleg` уже
      делегирует STI, а `sie.STIE` включён) и гасит `mie.MTIE` (иначе
      re-trap на каждой инструкции, пока компаратор не перевзведён).
      `mscratch` на каждый харт указывает на свою строку
      `G_MTRAP_SCRATCH` (по образцу `sscratch` в `trap_asm.rs`) — ни
      один регистр не трогается без save/restore, MTI может прервать
      произвольный S-mode код. Подключено per-hart: `boot.rs` (hart 0) и
      `arch/smp/secondary.rs` (harts 1..N, у них свой M-mode сетап).
      `srv::timer::arm_timer` унифицирован — `smode` и rv64-non-smode
      теперь оба идут через `arch::sbi::set_timer` (rv32-non-smode пока
      остаётся на старом прямом CLINT MMIO — `mtrap.rs` есть только для
      rv64, см. TODO там же). `sys_nanosleep` возвращён к паттерну
      idle-loop (`timer::init_hart` + `set_sstatus(SIE)` + `wfi` в
      цикле) — теперь реально работает, а не просто выглядит правильно.
      **Живое подтверждение** (QEMU, `-M virt -smp 2`, диагностический
      `/bin/init` = `init/src/sleep_test.rs`, добавлен как
      `[[bin]] onyx-sleep-test`): `before uptime_us=10000` →
      `nanosleep returned 0` → `after uptime_us=510000` — ровно 500мс,
      воспроизведено дважды подряд; полная загрузка боевого образа до
      login prompt тоже проверена (SMP/virtio-blk не сломаны). cargo
      build (rv64+rv32), clippy -D warnings (оба таргета), cargo test
      (146 passed) — всё чисто.
      Заодно найден и исправлен независимый latent-баг, который
      вскрылся при первой Sstc-попытке (когда тики стали доходить до
      S-mode впервые за всю историю этого QEMU-бута):
      `virtio_input::poll()` разыменовывал `G_IN.used` без проверки, что
      устройство вообще было пробировано (`G_IN.base != 0`) — раньше
      никогда не проявлялся именно потому, что таймерные тики не
      доходили. Guard добавлен (`kernel/src/drivers/virtio_input/decode.rs`).
      **Осталось на будущее**: rv32-таргет по-прежнему использует старый
      прямой CLINT MMIO путь для арминга таймера (см. TODO в
      `srv::timer::arm_timer`'s doc comment и `arch/asm/mod.rs`) — то же
      самое MTIP→STIP не-форвардится и для rv32 wfi-ожиданий; не чинил
      (rv32 — вторичный таргет проекта), нужен `arch/asm/mtrap_32.rs` по
      аналогии, если понадобится.
- [x] **Указатели рядом с `USER_TOP` (0x40000000) проваливали
      `user_ptr_ok`/`parse_user_path`, включая `argv`-строки** —
      **СДЕЛАНО 2026-09-03**. `parse_user_path` (`kernel/src/syscall/
      handler/dispatch.rs`) требовала безусловные 256 валидных байт за
      указателем; `argv[N]`, которые лоадер кладёт у самой вершины
      стека (`ustack=0x...3ffffff0` в логах), давали `path + 256 >
      USER_TOP` и получали `EINVAL`, даже когда сама строка целиком лежала
      в замапленной памяти (живой пример: `ohttp` не мог открыть свой же
      `argv[2]`). Исправлено: окно валидации теперь ограничивается
      `min(256, USER_TOP - path)` вместо жёстких 256 — проверяется и
      читается ровно столько байт, сколько реально может уместиться перед
      `USER_TOP`, а не фиксированный запас. `user_ptr_ok` (общая проверка
      диапазона) не трогали — баг был только в этой более строгой
      256-байтовой обвязке для путей/строк.

      глубоко в `dns_resolve`) — а не только для прерывания,
      заставшего процесс в user-mode (обычный, единственный
      предполагаемый случай верхнеуровневого резюмирования).
      `sched_yield` в таком вызове сохраняет ВЛОЖЕННЫЙ, невернеуровневый
      trap frame как `(*current).tf`; при последующем реальном
      переключении на этот процесс (когда параллельно runnable другой
      процесс, напр. родительский `osh` в `wait()`) резюмирование по
      этому кадру ломает состояние процесса — крашится на его следующем
      syscall'е. Воспроизводилось стабильно и на `-smp 1`.
      Исправлено в `kernel/src/srv/trap.rs`: `sched_yield` в конце
      `handle()` теперь вызывается, только если прерывание либо застало
      idle-харт (`current` = null), либо реально прервало user-mode
      (`sstatus.SPP == 0`, захвачено один раз в начале `handle()` как
      `interrupted_user`) — т.е. только когда `tf` гарантированно
      верхнеуровневый резюмируемый кадр. Для вложенного kernel-mode
      прерывания (SPP=1, `current` не null) тик всё равно полностью
      обслуживается (таймер/watchdog/event pump), просто решение о
      реальном переключении откладывается до следующей безопасной
      точки — `G_NEED_RESCHED` остаётся выставленным и не теряется.
      `net::dns_resolve` вернул `sys_nanosleep`-паттерн SIE+`wfi()`
      вместо busy-poll'а по `read_time()`. Живой QEMU-тест: `dnstest`
      резолвит `example.com` без единого краша на `-smp 1` и `-smp 2`
      (несколько прогонов подряд), `cargo test` — 146/146, `clippy` —
      чисто.

- [x] **SMP-краш под `-smp 2` (idle-харт, "illegal instruction" / битые
      pid/root_pa) — ЧАСТИЧНО ИСПРАВЛЕНО 2026-09-04.** Обнаружено
      2026-09-03 при живом QEMU-тесте `ohttp`; независимо воспроизведено
      2026-09-04 минимальным репро (без сети): под `-smp 2`, любой
      `exit` из `osh`, как только init мигрирует на второй харт через
      work-stealing. Три отдельных бага найдены и закрыты живым
      QEMU-тестированием (build → repro → fix → repro, по 5-6 прогонов
      на каждый):

      1. **Корневая причина мусорных pid/hartid**: `tp` (x4) —
         самодельный per-hart идентификатор (`hart_id()` = сырое
         `mv {0}, tp`, на нём держится весь планировщик:
         `G_HART_CURRENT`, runqueue, idle-контексты) — НЕ был
         зарезервирован флагом компилятора. LLVM был волен использовать
         `tp` как обычный scratch-регистр в любой скомпилированной
         функции, тихо портя hart-id посреди выполнения. Отсюда и
         "отрицательный pid" / битый `root_pa` из исходного репорта —
         это были panics в `current_pid()`
         (`G_HART_CURRENT[hart_id()]`) с мусорным индексом,
         маскирующиеся под сырой CPU-краш. Проявляется только под
         реальным SMP (на одном харте `hart_id()` всегда 0, паника по
         границам массива никогда не срабатывает). Фикс:
         `-C target-feature=+reserve-x4` добавлен в rustflags обоих
         таргетов (`.cargo/config.toml`) — тот же механизм, которым
         Linux на RISC-V защищает per-CPU `tp`.
      2. **`G_HART_IDLE_TF[0]` никогда не инициализировался.**
         Загрузочный харт (0) никогда не вызывает
         `sched_enter_idle()` — он сразу уходит в `enter_user(1)`
         (`srv::main::init::launch`) и может работать непрерывно, пока
         все процессы либо не мигрируют на другой харт через
         work-stealing, либо не завершатся. Когда `sched_yield`
         впервые пытался переключить hart 0 в простой, он резюмировал
         `G_HART_IDLE_TF[0]` — всё ещё `TrapFrame::zero()` (sepc=0,
         sp=0) — мгновенный краш при переключении. Фикс: новый флаг
         `G_HART_IDLE_TF_VALID[hart]` (`proc/process/globals.rs`);
         если харт ни разу не захватывал реальный idle-контекст,
         `sched_yield` прыгает прямо в свежий `sched_enter_idle()`
         (raw asm, те же явные регистры `t0`/`t1`, что и в п.1, а не
         generic `in(reg)`, чтобы не рисковать повторно зацепить
         `tp`) вместо резюмирования никогда не сохранённого кадра.
      3. **Гонка на UART** — `kinf!`/`kerr!` и `sys_write` писали в
         общий MMIO-регистр без какой-либо синхронизации между
         хартами, из-за чего лог краша интерливился побайтово и был
         нечитаем именно в момент, когда диагностика нужнее всего.
         Фикс: reentrant-по-харту лок (`srv/klog.rs::UART_LOCK`,
         используется также в `syscall/fs_sys/read_write.rs`) —
         reentrant специально для того, чтобы фолт, случившийся ВНУТРИ
         печати другого фолта на том же харте, не самозадедлочился.
      4. Заодно: `illegal instruction`/`brk` на `pid=0` (idle-харт без
         процесса) раньше падали в `proc::exit(0, ..)` — no-op — и
         тихо резюмировали ТУ ЖЕ инструкцию, зацикливаясь в бесконечный
         спам лога. Теперь такой фолт на `pid=0` уходит в `halt()`
         сразу (`srv/trap.rs`).
      5. Отдельно, не связано с этим SMP-путём: `destroy_root`/
         `free_subtree` (`mm/vmm/root.rs`) освобождал leaf-страницы,
         не проверяя `PTE_U`, — потенциально мог освобождать
         non-`PTE_U` identity-плейсхолдеры ядра. В данном случае они
         были вне managed-диапазона (`pmm::is_managed` их и так
         отсекал), так что это не было триггером ИМЕННО этого краша,
         но осталось верной защитой на будущее — оставлено в коде.

      закоммичено, легко воспроизвести):

      A. `steal()` пропатчен возвращать `null` всегда (work-stealing

      B. `steal()` оставлен КАК ЕСТЬ (работает нормально), но ветка
         "переключить харт в idle" в `sched_yield` пропатчена звать
         `klog::halt()` СРАЗУ вместо резюма через
         `seed_boot_hart_idle_context`/`sched_switch` → **тоже 0 фолтов
         из 10 прогонов**.

      Вывод однозначный: миграция процессов между хартами (`steal()`,
      `runqueue.rs`) сама по себе КОРРЕКТНА — проблема не в ней. Баг
      конкретно в МЕХАНИЗМЕ РЕЗЮМА idle-контекста hart0 (п.6 выше,
      `seed_boot_hart_idle_context` + резюм через
      `sched_switch`/`trap_return`) — именно ЭТА ветка кода и есть
      источник остаточного краша. `steal()` тут ни при чём, он просто
      единственный способ, которым hart0 вообще ДОХОДИТ до этой ветки
      (без стилинга hart0 никогда не остаётся без работы, значит
      никогда не вызывает эту ветку). Гипотеза про "гонку над
      `Proc.tf` в exit/steal/dequeue" из предыдущей записи —
      ОТВЕРГНУТА этим экспериментом, можно не тратить время на неё.

      Статически перечитан код `seed_boot_hart_idle_context` +
      `trap_return` (`arch/asm/trap_asm.rs`) построчно — видимых багов
      не нашёл: sstatus.SPP=1 корректно ведёт в `.Lret_kernel`
      (sscratch=0, как и требует `sched_enter_idle`), `tp`/`gp`
      корректно копируются из живых регистров в момент сидирования,
      `satp` — из `csr::read_satp()` на момент сидирования (то есть
      ДО первого `enter_user`, значит это `G_KERNEL_ROOT_PA`, который
      никогда не освобождается — не должно протухать). Единственное,
      что НЕ проверено: реальные ЗНАЧЕНИЯ этих полей в момент краша
      (не только код, который их пишет) — нужна живая инспекция.

      **Продолжение 2026-09-04 (пятая волна) — НАЙДЕН РЕАЛЬНЫЙ
      ГЛУБИННЫЙ КОРЕНЬ, подтверждён живыми прогонами**:

      Добавленная точечная диагностика (п. выше) поймала: два ПОЛНЫХ
      вызова принта `IDLESW hart=0 sepc=... sp=... satp=... gp=... tp=...`
      интерливились побайтово между собой, ОБА со значением `hart=0` —
      при том что `UART_LOCK` гарантирует взаимоисключение для ОДНОГО
      харта. Единственное разумное объяснение: **оба физических харта
      одновременно думали, что они hart 0** — то есть `tp` (регистр,
      на котором держится весь `hart_id()`) был испорчен так, что оба
      харта читали одно и то же значение.

      Проверка дизассемблера релизного `onyx-kernel.elf` нашла причину
      мгновенно: `drop_to_user` (`arch/asm/trap_asm.rs`), при переходе
      из ядра в user-mode, ЯВНО обнуляет ВСЕ регистры общего назначения
      перед `sret` — включая `gp` И `tp` (`li tp, 0`), как часть
      старого фикса "Bug (syscall MINOR #5)" (гигиена регистров, чтобы
      userspace не читал через inline asm чувствительные данные ядра
      типа указателей на kernel-стек). Но `tp` в этом ядре — НЕ обычный
      callee-saved регистр, это САМОДЕЛЬНЫЙ per-hart identity register
      (`hart_id()` = сырое `mv reg, tp`, на нём держится ВЕСЬ
      планировщик). После `li tp, 0` любой userspace-процесс исполняется
      с `tp=0`; когда этот процесс потом трапит обратно в ядро (ЛЮБОЙ
      syscall, таймерное прерывание, page fault) — на ЛЮБОМ физическом
      харте — `hart_id()` возвращает 0, независимо от того, какой
      харт реально исполняет код. Плюс отдельно: `trap_return`
      (тот же файл) ВСЕГДА восстанавливал `tp` из поля `tf.tp`
      trap-фрейма при возврате — а `create_user`
      (`proc/spawn/mod.rs`) никогда явно не устанавливает `tf.tp`,
      оно остаётся `0` по умолчанию (`TrapFrame::zero()`) для КАЖДОГО
      новосозданного процесса — второй, независимый путь того же
      обнуления.

      Это, вероятно, САМАЯ глубокая причина исходного SMP-краша —
      она существовала задолго до этой сессии (drop_to_user писался
      для решения СОВСЕМ другой проблемы, безо всякой связи с SMP) и
      просто никогда не проявлялась под `-smp 1`, где `hart_id()`
      всегда законно возвращает 0 в любом случае.

      **Фикс** (`kernel/src/arch/asm/trap_asm.rs` +
      `trap_asm_32.rs`):
      - `drop_to_user`: убрано `li tp, 0` (оставлен `li gp, 0` —
        `gp` не имеет для ядра особого смысла, а живая проверка
        (`grep -rn '\btp\b' OnyxCompiller`) подтвердила, что userspace
        (`libonyxc`/`onyxcc`) вообще нигде не читает `tp` — TLS или
        что-то подобное на нём не завязано, так что оставлять в нём
        hart id при входе в user-mode ничего не "утекает" (в отличие
        от указателей на kernel-стек, которые обнуляются намеренно).
      - `trap_return`: убрано `ld tp, 24(sp)` — при возврате ИЗ ловушки
        `tp` вообще больше не трогается. К этому моменту исполнение
        всё ещё идёт как код ядра НА РЕАЛЬНОМ физическом харте, так
        что в `tp` уже лежит корректное значение — резюмировать его
        из (возможно устаревшего/несозданного) trap-фрейма было в
        принципе неверно.

      **Результат**: после этого фикса живые прогоны (11 из 15 под
      стресс-тестом) стали ПОЛНОСТЬЮ ЧИСТЫМИ логами — ни одного байта
      мусора, ни одной "IDLESW hart=0"-путаницы. Но краш **не исчез
      полностью** — просто стал совершенно другим, узким и понятным:
      чистый `trap: KERNEL page fault pid=1 (init) hart=1 scause=0x7
      (store/AMO access fault) sepc=0x8020dc5a stval=0x0 a7=30
      (SYS_chan_recv)`. Дизассемблер показал: `sepc` попадает точно на
      `sb zero,0(s10)` внутри `sched_yield`'s affinity-migration ветки
      (`sched.rs:137-139`,
      `(*G_RQ.as_mut_ptr())[target].lock.unlock()`), с `s10` (адрес
      поля `locked` спинлока) равным НУЛЮ. Поскольку `affinity`
      инициализируется в `-1` и для init/osh/login никогда явно не
      меняется (`target == hartid` должно ПОЧТИ ВСЕГДА держаться,
      минуя эту ветку целиком), похоже на то, что `next`
      (результат `dequeue(hartid)`) — БИТЫЙ/чужой указатель, чьё поле
      `affinity` читает мусор, похожий на валидный номер харта. Не
      успел докопаться дальше — сессия близка к пределу.

      **Рекомендация для следующего захода** (теперь узко
      сфокусирована на НОВОМ, гораздо более простом баге): проверить,
      действительно ли `next` в `sched_yield` — валидный, живой `Proc`
      именно в этой конкретной ветке (строки ~106-146). Первый
      подозреваемый: гонка между `exit()`'s циклом очистки очередей
      (`for h in 0..MAX_HARTS { rq_lock(h); remove(h, p_ptr); rq_unlock(h) }`,
      `lifecycle/exit.rs`) — который лочит каждый харт ПООЧЕРЁДНО, не
      атомарно по всем сразу — и одновременным `dequeue()`/`steal()`
      того же самого `Proc` другим хартом в узком окне между
      разлочиванием одной очереди и залочиванием следующей. Точечная
      диагностика: залогировать адрес `next` и `(*next).affinity`
      сразу после `let mut next = dequeue(hartid);` (строка 107) и
      сверить, совпадает ли `next`'s pid с ожидаемым/живым процессом в
      момент печати.
- [ ] Бо́льшие recv-буферы / recv semantics — `tcp_recv` сейчас никогда
