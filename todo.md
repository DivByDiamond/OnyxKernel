#### Баг A (корневой, ломает всю систему, не только консоль): 100 Гц таймер умирает через ~5 тиков

**Факты (замеры `xp` по `G_JIFFIES`/`G_UPTICKS`):**

| t, с | JIFFIES | UPTICKS | present_tick calls | presents |
|------|---------|---------|--------------------|----------|
| 12   | 5       | 5       | 5                  | 0        |
| 48   | 5       | 5       | 5                  | 0        |

Тик встаёт намертво: 5 тиков (~50 мс) и всё, дальше 36+ секунд ноль движения.

**Состояние CSR в момент зависания (`info registers`):**
- `priv = S`, `scause = 8` (ecall из U-mode) — ядро внутри системного вызова;
- `sstatus = 0x…44020` → **`SIE` (бит 1) = 0**, `SPP` (бит 8) = 0 (пришли из user);
- `sip = 0x20` → **`STIP` взведён**, `sie = 0x222` → `STIE` разрешён;
- `mie = 0x222` → **`MTIE` (бит 7) сброшен**, `mip = 0xa0` (MTIP+STIP взведены);
- CLINT: `mtime = 0x0be56341` (199.5 M) **уже далеко за** `mtimecmp = 0x054d6bea` (89.1 M);
- застрявший `pc = 0x80207ad0` → `onyx_kernel::drivers::uart::getc`.

**Цепочка причин.**
1. `login` висит в `read(0,…)` → `console_read` → `first_byte`/`cooked_read`
   (`syscall/fs_sys/console_read.rs`) крутят busy-poll `uart::getc()` +
   `proc::sched_yield(tf)`.
2. Ядро исполняется с `sstatus.SIE = 0` (осознанный инвариант «SIE=0 запрещает
   вытеснение на том же харте», см. `crate::sync`). Прерывание S-таймера
   доставляется только когда харт **в U-mode** или когда кто-то явно включит SIE.
3. `login` — единственный runnable процесс, поэтому `sched_yield` возвращается
   в него же **не выходя в U-mode** и **не заходя в idle-петлю**. А включают SIE
   только `proc/scheduler/idle.rs:152` и `syscall/fs_sys3/time.rs:152`.
   `console_read` не включает SIE нигде → взведённый `STIP` не доставится никогда.
4. Раз `srv::timer::handle()` не вызвался — не вызвался и `arm_timer` →
   не ушёл ecall `SBI_SET_TIMER` → M-mode-форвардер `arch/asm/mtrap.rs`
   **не переармировал `mie.MTIE`** (он гасит MTIE в `.Lm_timer_fwd` и включает
   обратно ТОЛЬКО в обработчике ecall) и не сдвинул `mtimecmp`.
5. Таймер мёртв **навсегда**. Вместе с ним: вытесняющее планирование,
   heartbeat watchdog'а, soft-таймеры, `srv::event::pump()` и
   `present_tick()` → задний буфер никогда не копируется во фронт → чёрный экран.

**Архитектурный корень:** handshake «MTIE гасим на тике, включаем только по
ecall'у» делает таймер **самоубийственным**: любое окно, в котором S-mode не
может принять STI, убивает тик не «с задержкой», а *насмерть*. Нужен либо
таймер, переармируемый независимо от S-mode, либо гарантия, что каждый
блокирующий путь в ядре открывает окно прерываний.

**Проверено экспериментально (диагноз подтверждён, патч откатан):** временная
вставка окна прерываний (`set_sstatus(SSTATUS_SIE)` / `nop` /

        настройка `mscratch`/`mtvec` → `mtrap_entry_32` (шаг вторичных

        идёт через `arm_timer()`/ecall, как rv64/smode; сырой CLINT MMIO
        (`write_mtimecmp`/`arm_timer_for_hart`) остался только как
        `cfg(test)`-заглушка для хостовых юнит-тестов.

      **Баг найден #1 (блокировал АБСОЛЮТНО любую загрузку rv32):**
      `mm/vmm/root.rs::init()`, Sv32-ветка писала ОДНУ PTE-запись по
      индексу 0 (VA/PA `0x0-0x3FFFFF`). DRAM на QEMU virt — фиксированно
      `0x80000000` (тот же физический layout, что и у rv64), а ядро
      грузится на `0x80200000+`. Индекс Sv32 top-level PTE = `PA >> 22`
      (4МБ мегастраницы) → для `0x80000000` это индекс **512**, не 0.
      Первая же выборка инструкции ПОСЛЕ `install_root()` (переключение
      `satp`) падала мгновенно — тихо, без паники (обработчик трапов ещё
      не поднят так рано). Плюс отдельно: `root` в этой функции типизирован
      как `*mut u64` для rv64-ветки — Sv32 PTE **32-битные**, и переиспользование
      этого указателя с `.add(index)` давало бы шаг 8 байт вместо 4 для
      любого индекса кроме 0. Фикс: отдельный `*mut u32`-вид + маппинг
      512МБ окна от DRAM_BASE (128×4МБ мегастраниц).

      **Баг найден #2 (тот же коммит, обнаружен сразу после фикса #1):**
      фикс #1 замапил только DRAM — но следующая же инструкция после
      влючения paging (`uart::putc(b'V')` в `early_init`) обращается к
      UART MMIO (`0x10000000` на QEMU virt), который остался немаплен →
      мгновенный краш ещё раз, просто чуть позже. У rv64 эта проблема
      никогда не проявлялась, потому что три гигабайтные страницы (индексы
      0,1,2 = `0x0-0xC0000000`) заодно покрывают CLINT/PLIC/UART/virtio
      И DRAM одним и тем же широким окном. У Sv32 4МБ-мегастраницы для
      этого слишком мелкие, чтобы дёшево покрыть весь диапазон — вместо
      этого замаплено ВТОРОЕ отдельное окно 512МБ от `0x0` (покрывает
      CLINT `0x02000000`, PLIC `0x0C000000`, UART/virtio `0x10000000+`).

      **Результат после обоих фиксов** (проверено живым QEMU:
      `qemu-system-riscv32 -M virt -bios none -kernel <rv32 elf>` через
      минимальный M-mode шим-загрузчик, т.к. у OnyxBoot нет rv32-порта):
      загрузка реально продвинулась с «падает на первой инструкции после
      pmm::init» до баннера → fdt → pmm → **vmm → heap → runqueue → trap
      init → `timer: CLINT @0x02000000, tick=100 ns`** (лог именно из
      `srv::timer::init()`, значит МОЙ фикс реально исполняется) → plic →
      перебор 8 virtio-узлов (устройств нет, т.к. диск не подключён в
      минимальном тесте) → rtc → hwrand.

      **Баг #3 — НАЙДЕН И ЗАКРЫТ (продолжение той же сессии):**
      `sepc` указывал ВНУТРЬ диапазона стека (`__stack_bottom..__stack_top`)
      — исполнение реально прыгнуло в содержимое стека как в код. Корень —
      `trap_asm_32.rs` был механическим `sd→sw`/`ld→lw` переводом
      `trap_asm.rs` (rv64), но байтовые офсеты полей ОСТАЛИСЬ rv64-шными
      (шаг 8: 0,8,16,24,32...), хотя `TrapFrame` на rv32 — 4 байта на поле
      (`TRAP_FRAME_SIZE=144`, 36×u32). Каждое поле, кроме `ra` (офсет 0,
      совпал случайно), попадало не в свой слот, а максимальный
      используемый офсет (280) — на 136 байт ЗА пределами реально
      зарезервированных `addi sp, sp, -144` 144 байт — то есть КАЖДЫЙ трап
      затирал память НАД кадром на стеке. Плюс полностью отсутствовало
      различение kernel/user-трапа (`bnez sp, .Ltrap_from_user` на входе,
      SPP-проверка на выходе у rv64) — при `sscratch==0` (маркер «трап из
      ядра», см. `srv::trap::init`) `csrrw sp, sscratch, sp` при трапе ИЗ
      ЯДРА оставлял `sp=0`, а `addi sp, sp, -144` заворачивался в
      `0xFFFFFF70` — дикий указатель стека для всего сохранения/
      восстановления. Невидимо раньше, потому что до этой сессии rv32
      никогда не долетал до первого настоящего S-mode трапа живьём. Файл
      переписан полностью с верными (делёнными на 2) офсетами и полным
      kernel/user-различением, портированным из `trap_asm.rs`.

      **Баг #4 — НАЙДЕН И ЗАКРЫТ:** после бага #3 загрузка продвинулась
      до `hwrand::next_u32()`, где `rdcycle` падал illegal instruction —
      `boot_32.rs` (в отличие от `boot.rs` и ОБЕИХ веток
      `arch/smp/secondary.rs`, включая её собственную rv32-ветку!) никогда
      не выставлял `mcounteren`, без которого S-mode не может читать
      `cycle`/`time`/`instret`.

      **Баг #5 — НАЙДЕН И ЗАКРЫТ:** после бага #4 загрузка дошла до
      `ramfb`/`fw_cfg`-пробирования и упала снова — `stval=0x30000000`
      (похоже на PCIe ECAM), вне обоих 512МБ-окон из фикса vmm выше.
      Вместо погони за отдельными адресами по одному — окно расширено до
      **точно того же физического диапазона, что и у rv64**: `0x0-0xC0000000`
      (3ГБ) одним циклом (768 Sv32-мегастраниц по 4МБ вместо 3 гигастраниц
      rv64 — набор физических адресов идентичен).

      **Итоговый результат (все 5 багов rv32 закрыты, живой QEMU
      подтверждает):** загрузка проходит ЧИСТО, без единого краха:
      баннер → fdt → pmm → vmm → heap → runqueue → trap init →
      `timer: CLINT @0x02000000, tick=100 ns` → plic → перебор virtio-узлов
      → rtc → hwrand → entropy → net → ramfb → fb → vfs/procfs/ipcfs/devfs
      → ожидаемое `open /bin/init failed: EINVAL` (в минимальном тесте без
      диска). Временным (не закоммиченным, откаченным сразу после
      проверки) патчем `klog::halt()` — чтобы не гасить `SIE` при
      ожидаемом EINVAL-краше без диска — подтверждено, что `G_JIFFIES`
      реально растёт со скоростью ~100/с (284→774→1265→1756 на
      t=5/10/15/20с). Таймер-фикс (A1-A3) теперь верифицирован ПОЛНОСТЬЮ
      живым прогоном, не только `cargo build`/`test`/`clippy`.

      **Инструменты для повтора/продолжения расследования** (временные,
      не закоммичены — воссоздать при необходимости): минимальный M-mode
      шим (`li t0, 0x80200000; jr t0`, собран `rustc --target
      riscv32imac-unknown-none-elf -C link-arg=-Ttext=0x80000000
      -C link-arg=--entry=_start --crate-type bin`, конвертирован в raw
      binary через `riscv64-linux-gnu-objcopy -O binary`) используется как
      `-bios` вместо реального OpenSBI/OnyxBoot (которых для rv32 просто
      нет), чтобы ядро реально стартовало в M-mode, как рассчитывает
      `boot_32.rs`. `G_JIFFIES`/CSR читаются тем же способом `xp` через
      monitor, что и во всём остальном расследовании этой сессии.

#### Баг B (независимый): генератор шрифта пишет PSF **без единого глифа**

Даже когда таймер починен и presents идут — текста по-прежнему нет.
Счётчики в `fb::draw::draw_char` показали: **597 вызовов** `draw_char`,
и при этом число глифов, в которых есть **хоть один установленный бит, — 0**.
Курсор виден только потому, что `draw_cursor_cell_front` заливает ячейку
напрямую, не заглядывая в шрифт.

**Корень — усечение целого в `tools/src/psfgen/generate.rs`:**

```rust
const GLYPHS: usize = 256;
...
for c in 0..GLYPHS as u8 {            // ← `as` связывает сильнее, чем `..`
    buf.extend_from_slice(glyph_bitmap(c));
}
```

Это парсится как `0..(GLYPHS as u8)`, а `256 as u8 == 0` → диапазон `0..0`
**пуст**, цикл не исполняется ни разу. В файл уходят только 4 байта заголовка
и 1024 байта unicode-таблицы.

Подтверждение на диске (`OnyxKernel/build/default.psf`,
`OnyxOS/.build/.tmp-onx/default.psf`): **1028 байт** = 4 + 0 + 1024, тогда как
должно быть 4 + 256·16 + 1024 = **5124**. Заголовок корректен
(`36 04` PSF1, mode `0x02`, charsize `0x10`), сразу за ним начинается
unicode-таблица `0000 ffff 0100 ffff …` — секции битмапов нет вообще.
Из-за этого ядро логирует `font: loaded /font/default.psf`, но каждый символ
рисуется фоном по фону, т.е. невидим.

- [x] **B1. ЗАКРЫТО 2026-09-12** — `for c in 0..GLYPHS { glyph_bitmap(c as u8) }`.
- [x] **B2. ЗАКРЫТО** — `assert_eq!(buf.len(), total_size, ...)` добавлен в `psf1()`.
- [x] **B3. Не нужен — перепроверено:** `font/psf1.rs::init_psf1` УЖЕ делал
      ровно этот санити-чек (`data.len() < 4 + glyph_bytes → Err(Errno::Io)`)
      до этой сессии — проверка существовала, просто была не тем, что
      скрывало баг. Реальная дыра была в `srv/main/vfs.rs::load_font`,
      которое печатало `"font: loaded"` даже когда `font::init(...)`
      возвращал `Err` (глотало ошибку через `.ok()`) — теперь исправлено,
      различает успех/провал.
- [x] **B4. Не является OOB — перепроверено:** ложная тревога первого
      прохода диагностики. Проверка длины в `init_psf1` (см. B3) срабатывает
      РАНЬШЕ, чем `G_FONT` вообще устанавливается — на битом 1028-байтном
      блобе `font::init` возвращает `Err` и `G_FONT` остаётся `None`, так
      что `glyph_bitmap()` уходит в `BLANK_GLYPH`, а не читает за пределы

**Порядок починки:** A и B независимы, но экран заработает только когда
закрыты ОБА (A — чтобы кадр вообще презентовался, B — чтобы в кадре было что
показывать). Критерий готово: загрузиться, подождать 10 с, `screendump` —

### 🔥 Найдено и починено при живом тесте ohttp в QEMU (2026-09-01)
Тестировал `OnyxApps/apps/ohttp` в QEMU (`-netdev user` + `guestfwd`); по ходу
нашлись и почищены два системных бага, плюс остался один открытый:

- [x] **Errno не транслировался в POSIX** — `core/src/errno.rs::Errno::as_i64()`
      отдавал «сырой» внутренний ordinal (`Ok=0, NoMem=-1, Inval=-2, NoEnt=-3,
      Io=-4, Perm=-5, ...`), и именно это число (после отрицания) попадало в
      userspace `errno`, хотя `libonyxc/include/io/errno.h` документирует и
      определяет POSIX/glibc-значения (`ENOENT=2, EIO=5, EACCES=13, ...`) и
      прямо утверждает, что трансляция уже происходит. Добавлены
      `Errno::to_posix()` / `Errno::from_i64()` / `Errno::translate_syscall_result()`
      (`core/src/errno.rs`, покрыты host-тестами) и единая точка перевода в
      `kernel/src/syscall/handler/dispatch.rs::handle()` (оборачивает и ACL-early-return,
      и результат матча по `nr`). Подтверждено живьём: `ohttp` до фикса получал
      `errno=4` (сырой `Io`), после фикса — `errno=5` (POSIX `EIO`).
- [x] **virtio-net не настраивал отдельную TX-очередь (queue 1)** —
      `send()` писал в те же кольца, что `setup_rx_queue` завела для очереди 0
      (RX), и уведомлял `R_QUEUE_NOTIFY` со значением `0` — то есть говорил
      устройству «в RX есть новые буферы» вместо «вот кадр на отправку», и
      затирал RX-дескрипторы 0/1. Заведена отдельная TX-очередь (`queue 1`,
      как у `virtio_console` — см. `kernel/src/drivers/virtio_console/mod.rs`
      для образца), `send()` теперь пишет в `G_NET.tx_*` и уведомляет
      `R_QUEUE_NOTIFY=1` (`kernel/src/drivers/virtio_net/mod.rs`,
      `kernel/src/drivers/virtio_net/xfer.rs`).
- [x] **virtio-mmio регистрировал очереди только по modern-протоколу (v2)** —
      реальный `qemu-system-riscv64 -device virtio-net-device` под `-M virt`
      по умолчанию отдаёт **legacy** транспорт (`R_VERSION=1`), у которого нет
      регистров `R_QUEUE_{DESC,AVAIL,USED}_*`/`R_QUEUE_READY` — вместо них
      нужен один `R_QUEUE_PFN` на физически смежный регион
      desc|avail|used, плюс `R_GUEST_PAGE_SIZE`/`R_QUEUE_ALIGN`. Драйвер писал
      только modern-регистры, так что на legacy-транспорте очередь физически
      никогда не «вооружалась» — отсюда 0 пакетов на pcap. Добавлен общий
      `setup_queue_rings(base, modern)` с legacy-веткой (по образцу
      `kernel/src/drivers/virtio/queue.rs::setup_queue`, который у virtio-blk
      уже делал это правильно). **Подтверждено pcap'ом**: до фикса — 0 пакетов
      за весь бут; после — полный DHCP DISCOVER/REPLY, ARP REQUEST/REPLY,
      TCP SYN → SYN-ACK от пира.
- [x] **DHCP OFFER доходил до RX-буфера корректно, но не засчитывался; TCP
      SYN-ACK матчился с той же ошибкой** — оба `handle_udp_inner`
      (`kernel/src/net/udp/rx.rs`) и `handle_tcp_inner`
      (`kernel/src/net/tcp/handle.rs`) читали src/dst port **в обратном
      порядке**: UDP/TCP-заголовок (RFC 768/793) кладёт source port в байты
      0-1, destination port — в байты 2-3, а оба обработчика были написаны

         `sched_yield` прыгает прямо в свежий `sched_enter_idle()`
         (raw asm, те же явные регистры `t0`/`t1`, что и в п.1, а не
         generic `in(reg)`, чтобы не рисковать повторно зацепить
         `tp`) вместо резюмирования никогда не сохранённого кадра.
      3. **Гонка на UART** — `kinf!`/`kerr!` и `sys_write` писали в
         общий MMIO-регистр без какой-либо синхронизации между
         хартами, из-за чего лог краша интерливился побайтово и был
         нечитаем именно в момент, когда диагностика нужнее всего.
         Фикс: reentrant-по-харту лок (`srv/klog.rs::UART_LOCK`,
         используется также в `syscall/fs_sys/read_write.rs`) —
         reentrant специально для того, чтобы фолт, случившийся ВНУТРИ
         печати другого фолта на том же харте, не самозадедлочился.
      4. Заодно: `illegal instruction`/`brk` на `pid=0` (idle-харт без
         процесса) раньше падали в `proc::exit(0, ..)` — no-op — и
         тихо резюмировали ТУ ЖЕ инструкцию, зацикливаясь в бесконечный
         спам лога. Теперь такой фолт на `pid=0` уходит в `halt()`
         сразу (`srv/trap.rs`).
      5. Отдельно, не связано с этим SMP-путём: `destroy_root`/
         `free_subtree` (`mm/vmm/root.rs`) освобождал leaf-страницы,
         не проверяя `PTE_U`, — потенциально мог освобождать
         non-`PTE_U` identity-плейсхолдеры ядра. В данном случае они
         были вне managed-диапазона (`pmm::is_managed` их и так
         отсекал), так что это не было триггером ИМЕННО этого краша,
         но осталось верной защитой на будущее — оставлено в коде.

      **Продолжение 2026-09-04 (пятая волна) — НАЙДЕН РЕАЛЬНЫЙ
      ГЛУБИННЫЙ КОРЕНЬ, подтверждён живыми прогонами**:

      Добавленная точечная диагностика (п. выше) поймала: два ПОЛНЫХ
      вызова принта `IDLESW hart=0 sepc=... sp=... satp=... gp=... tp=...`
      интерливились побайтово между собой, ОБА со значением `hart=0` —
      при том что `UART_LOCK` гарантирует взаимоисключение для ОДНОГО
      харта. Единственное разумное объяснение: **оба физических харта
      одновременно думали, что они hart 0** — то есть `tp` (регистр,
      на котором держится весь `hart_id()`) был испорчен так, что оба
      харта читали одно и то же значение.

      Проверка дизассемблера релизного `onyx-kernel.elf` нашла причину
      мгновенно: `drop_to_user` (`arch/asm/trap_asm.rs`), при переходе
      из ядра в user-mode, ЯВНО обнуляет ВСЕ регистры общего назначения
      перед `sret` — включая `gp` И `tp` (`li tp, 0`), как часть
      старого фикса "Bug (syscall MINOR #5)" (гигиена регистров, чтобы
      userspace не читал через inline asm чувствительные данные ядра
      типа указателей на kernel-стек). Но `tp` в этом ядре — НЕ обычный
      callee-saved регистр, это САМОДЕЛЬНЫЙ per-hart identity register
      (`hart_id()` = сырое `mv reg, tp`, на нём держится ВЕСЬ
      планировщик). После `li tp, 0` любой userspace-процесс исполняется
      с `tp=0`; когда этот процесс потом трапит обратно в ядро (ЛЮБОЙ
      syscall, таймерное прерывание, page fault) — на ЛЮБОМ физическом
      харте — `hart_id()` возвращает 0, независимо от того, какой
      харт реально исполняет код. Плюс отдельно: `trap_return`
      (тот же файл) ВСЕГДА восстанавливал `tp` из поля `tf.tp`
      trap-фрейма при возврате — а `create_user`
      (`proc/spawn/mod.rs`) никогда явно не устанавливает `tf.tp`,
      оно остаётся `0` по умолчанию (`TrapFrame::zero()`) для КАЖДОГО
      новосозданного процесса — второй, независимый путь того же
      обнуления.

      Это, вероятно, САМАЯ глубокая причина исходного SMP-краша —
      она существовала задолго до этой сессии (drop_to_user писался
      для решения СОВСЕМ другой проблемы, безо всякой связи с SMP) и
      просто никогда не проявлялась под `-smp 1`, где `hart_id()`
      всегда законно возвращает 0 в любом случае.

      **Фикс** (`kernel/src/arch/asm/trap_asm.rs` +
      `trap_asm_32.rs`):
      - `drop_to_user`: убрано `li tp, 0` (оставлен `li gp, 0` —
        `gp` не имеет для ядра особого смысла, а живая проверка
        (`grep -rn '\btp\b' OnyxCompiller`) подтвердила, что userspace
        (`libonyxc`/`onyxcc`) вообще нигде не читает `tp` — TLS или
        что-то подобное на нём не завязано, так что оставлять в нём
        hart id при входе в user-mode ничего не "утекает" (в отличие
        от указателей на kernel-стек, которые обнуляются намеренно).
      - `trap_return`: убрано `ld tp, 24(sp)` — при возврате ИЗ ловушки
        `tp` вообще больше не трогается. К этому моменту исполнение
        всё ещё идёт как код ядра НА РЕАЛЬНОМ физическом харте, так
        что в `tp` уже лежит корректное значение — резюмировать его
        из (возможно устаревшего/несозданного) trap-фрейма было в
        принципе неверно.

      **Результат**: после этого фикса живые прогоны (11 из 15 под
      стресс-тестом) стали ПОЛНОСТЬЮ ЧИСТЫМИ логами — ни одного байта
      мусора, ни одной "IDLESW hart=0"-путаницы. Но краш **не исчез
      полностью** — просто стал совершенно другим, узким и понятным:
      чистый `trap: KERNEL page fault pid=1 (init) hart=1 scause=0x7
      (store/AMO access fault) sepc=0x8020dc5a stval=0x0 a7=30
      (SYS_chan_recv)`. Дизассемблер показал: `sepc` попадает точно на
      `sb zero,0(s10)` внутри `sched_yield`'s affinity-migration ветки
      (`sched.rs:137-139`,
      `(*G_RQ.as_mut_ptr())[target].lock.unlock()`), с `s10` (адрес
      поля `locked` спинлока) равным НУЛЮ. Поскольку `affinity`
      инициализируется в `-1` и для init/osh/login никогда явно не
      меняется (`target == hartid` должно ПОЧТИ ВСЕГДА держаться,
      минуя эту ветку целиком), похоже на то, что `next`
      (результат `dequeue(hartid)`) — БИТЫЙ/чужой указатель, чьё поле
      `affinity` читает мусор, похожий на валидный номер харта. Не
      успел докопаться дальше — сессия близка к пределу.

      **Рекомендация для следующего захода** (теперь узко
      сфокусирована на НОВОМ, гораздо более простом баге): проверить,
      действительно ли `next` в `sched_yield` — валидный, живой `Proc`
      именно в этой конкретной ветке (строки ~106-146). Первый

      (`for h in 0..MAX_HARTS { rq_lock(h); remove(h, p_ptr); rq_unlock(h) }`,
      `lifecycle/exit.rs`) — который лочит каждый харт ПООЧЕРЁДНО, не
      атомарно по всем сразу — и одновременным `dequeue()`/`steal()`

        (spawn/exit-шторм ~200/сек, тысячи циклов без единого фолта).
      - Старая сигнатура `scause=0x7 s10=0 в affinity-ветке sched_yield`
        больше не наблюдалась НИ РАЗУ; гипотеза про гонку exit()/steal()
        в dequeue не подтвердилась и не опроверглась — она просто
        перестала быть актуальной как описание текущего фолта. Новый
        фолт = испорченное ra (или sp→чужой стек) на kernel stack
        pid 1 в окне spawn+exec: возврат по ra=юзер-тексту мёртвого
        ребёнка при активном ядерном satp.
      - Статус в трекере: вынесено в отдельный открытый пункт
        "SMP: instruction page fault на тексте мёртвого процесса в
        окне respawn" (см. КРИТИЧНО ниже).

      **ПОПЫТКА ФИКСА 2026-09-08 (три волны, сужает, но НЕ закрывает)**:
      Автоматизированный стресс-харнесс (pexpect-стиль, boot→login→exit,
      11-12 прогонов на волну) + дизассемблер релизного ELF. Три
      конкурирующих механизма найдены и закрыты в коде (см. коммит
      "fix(smp): respawn-race hardening" — sched.rs, exit.rs, mtrap.rs,
      smp.rs, csr.rs, regs.rs, trap.rs):
      1. **Гонка exit() ↔ dequeue/steal (in-flight Proc)**: exit публиковал
         Exited ПОД proc_list_lock, но удалял из runqueue'й ПООЧЕРЁДНО
         (rq_lock(h) по одному), поэтому чужой dequeue мог забрать узел,
         пока exit не дошёл до его очереди; реап kfree'ил Proc, следующий
         spawn получал ту же память → резюм чужого tf (у которого ra =
         юзер-текст мёртвого ребёнка = 0x12000). Фиксы: (a) Ready-guard в
         sched_yield — dequeued/stolen узел с состоянием != Ready
         отбрасывается без резюма (sched.rs, оба места); (b) exit() теперь
         держит ВСЕ rq-локи (по возрастанию — дедлок-фри, все остальные
         держат максимум один) поверх публикации Exited + remove из всех
         очередей (exit.rs).
      2. **Отсутствие cross-hart TLB shootdown**: destroy_root() делал
         только ЛОКАЛЬНЫЙ sfence.vma_all — другой харт, на котором процесс
         когда-то исполнялся (work-stealing), держал TLB-записи юзер-VA →
         уже освобождённые кадры; запись через устаревший TLB после
         переаллокации портила ЧУЖУЮ память (в т.ч. page-table страницы
         следующего login) — объясняет варианты "load fault 0x15000 внутри
         kinf!-форматирования" (мусорный &str) и мусорный hexdump-поток +
         "attempt to subtract with overflow". Фикс: полноценный IPI
         shootdown — destroy_root рассылает S-soft IPI всем online-хартам
         через новый arch::smp::send_soft_ipi (CLINT msip, regs.rs
         clint_msip_hart), mtrap_entry (M-mode, mtrap.rs .Lm_soft_fwd)
         гасит MSIP и взводит mip.SSIP, S-mode обработчик INTR_S_SOFT
         (srv/trap.rs) ack-ит SSIP (csr.rs: новый clear_sip/read_sip/
         set_sip) и делает sfence_vma_all на своём харте.
      3. **Порядок publish/removal**: раньше Exited публиковался ПОСЛЕ
         начала снятия с очередей — теперь публикация всегда под всеми
         rq-локами, так что окно "dequeue до публикации" закрыто
         полностью.
      **Результат волн**: базовая линия 6/11 фолтов (ra=0x12000 ~100%
      сигнатур). После v1 (Ready-guard): ra=0x12000 почти исчез, вылезли
      ЛИКВИДИРОВАННЫЕ маскировкой варианты (0x15000-нагрузка, illegal
      instr pid=3/4, hexdump+subtract-panic). После v2+v3: ra=0x12000
      всё ещё доминирует (2/12 clean под -smp 2; 1/4 clean под -smp 8,
      те же sepc=0x12000 на hart 2/3). Все три фикса оставлены в коде —
      каждый закрывает РЕАЛЬНОЕ окно, но остался четвёртый путь.
      **ВОЛНА 4 — КОРЕНЬ НАЙДЕН И ЗАКРЫТ (2026-09-08, фикс `ipc::disconnect_waiter`)**:
      Ведущий с волны 3 (sp=0x80282238 — это HEAP, т.е. ЧУЖОЙ kstack в
      переиспользованном Proc-блоке, а не статика ядра) привёл к
      readdir по всем держателям сырых `*mut Proc`. Нашёлся: IPC-каналы
      (`ipc/channel/ringbuf.rs::wait_enqueue`) кладут сырой указатель
      текущего Proc в `send_wait`/`recv_wait`, но НИКТО не вычищал
      умирающий процесс из этих списков — `exit()` их не обходил, а
      `wait_wake_all` при следующем wake писал `state=Ready` /
      `wait_next=null` СКВОЗЬ ОСВОБОЖДЁННЫЙ указатель — ровно в поля
      того живого процесса, который получил эту память от `alloc_proc`
      (state — offset 5, tf — offset ~624, wait_next — ~65560). При
      respawn-шторме (~200 циклов spawn/exit в секунду через
      initd_req/initd_resp) узлы рециклировались постоянно — порча
      tf/alive-Proc давала весь наблюдаемый зоопарк: прыжки в текст
      мёртвого ребёнка (ra=0x12000), illegal instruction с sepc
      мёртвого lsblk (0x1008 — lsblk-сервис создаётся и гаснет на
      раннем буте), мусорные &str в kinf! (load fault 0x15000),
      hexdump-поток + subtract-overflow в userspace.
      **Фикс**: `ipc::disconnect_waiter(p)` — exit() перед возможным
      reапом вычищает указатель изо всех wait-списков всех каналов
      (чистое сравнение указателей, без разыменования p; под локом
      каждого канала).
      **РЕЗУЛЬТАТ**: стресс boot→login→exit — **12/12 clean под -smp 2,
      6/6 clean под -smp 8** (было 6/11 фолтов под -smp 2 до всей серии).
      Все четыре механизма (in-flight Proc, publish/removal порядок,
      cross-hart TLB, IPC wait-листы) закрыты; SMP-специфичный
      respawn-краш больше не воспроизводится. Стресс-харнесс закоммичен:
      `scripts/smp_respawn_stress.sh` (bash, N прогонов boot→login→exit с
      классификацией фолтов), для journal e2e —
      `scripts/onyxfs_journal_e2e.sh` + `scripts/onyxfs_journal_inject.c`.
- [ ] Бо́льшие recv-буферы / recv semantics — `tcp_recv` сейчас никогда
